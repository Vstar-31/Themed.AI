## 4. Execution order and estimates

1. **World fix first.** Keep the two one-widget fixtures distinct. Baseline both Studio and Desktop World. After patching, alternate them 20 times using the formerly failing button. At every switch record requested world, actual visible host, enabled skin ID, coordinates and active ID. Repeat during playback, interrupt one apply in a test fixture, then restart. Green Windows CI and the GUI evidence are the desktop merge criteria.
2. **Playlist fix in parallel.** Use the module branch and its existing React page. Run `npm test` and `npm run build` in `frontend/`. Capture the same five-track result at both window sizes, with the sidebar open, through an actual desktop WebView. Confirm that narrowing the window moves controls to another line while title, artist and buttons remain usable.
3. **Start the 48-hour test early.** Use the corrected desktop binary, isolated app/browser data and a stable machine. A reboot or changed PID starts a new run. During the soak, work through the other beta rows. Complete hardware tests on a dedicated setup. Keep the sign-key rollout deferred until the operator chooses the window.
4. **Ship the limited beta, then the signed public candidate.** Close blocker regressions on the shipped revision. Record repro steps, expected vs actual, environment, evidence and residual limits for every failure. Re-run the affected scenarios after each fix.

**Planning range.** The existing release plan budgets **2–4 working weeks for a limited beta** and **6–10 working weeks total for signed public v1**, assuming one full-time developer, a fixed v1 scope, an affected Windows machine, mixed-DPI hardware, a clean VM and signing access. These are planning ranges from the November review. The two newly reproduced UI defects, the soak result and rollout timing warrant re-estimation after the first corrected GUI pass. A deferred production change has no committed calendar date.
