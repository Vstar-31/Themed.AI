# Themed.AI release plan

Planning baseline: 14 November 2026. See the [project report](../phases.md) for shipped features, branch ownership and evidence. The dates below are estimates for one developer working five focused days per week, with timely access to an unlocked Windows machine, a mixed-DPI display setup, a clean VM and signing credentials. The proposed v1 scope is the existing desktop, authoring, sharing, automation and music experience. Confirm that scope when selecting a release candidate.

## Release sequence

| Order | Work and dependency | Exit evidence | Effort |
| --- | --- | --- | --- |
| 1. Reproduce and classify | Pin the desktop and module revisions. Recheck the signed-in genre labels in the regular build. Start a 48-hour soak on the affected hybrid-GPU machine early, covering minimize/restore, sleep/wake and navigation. Record app/SDK/driver versions and compare screenshots before and after. | Classify each rendering issue as reproduced, fixed and retested, or still open. Record restart recovery and any limits for testers. | 2–4 developer days, with elapsed soak time overlapping other work |
| 2. Close desktop regressions | Exercise 100/150/200% scale, negative monitor coordinates, unplug/replug, taskbar edges, rapid world changes during playback, storage failure/retry, tray exit and restart. Transfer a grouped image-bearing package to a second machine with the source image absent; edit and re-export it. Check keyboard-only creation, palette undo, style switching, automation signals and network loss. | Expected placements, reachable controls, recoverable saves, preserved assets and one active world on restart. Record failures by build and retest fixes. | 4–8 days |
| 3. Finish endpoint and data review | Reconcile the three security PRs with their intended bases. Inventory HTTP routes, OAuth callbacks, external proxies and desktop bridge messages. Record which routes are public, which need authentication and which also need ownership checks. Review credential storage, logging, provider limits and outstanding account-data questions. | Reviewed patches and tests on intended branches, deployment/configuration verified, access and ownership regression checks, signed-in smoke tests, findings recorded with disposition. Desktop snapshot review alone cannot close the production-backend item. | 4–8 days |
| 4. Issue the tester beta | Collect the bounded fixes, run clean Windows CI, and publish an identified x64 build with setup, backup, recovery, feedback instructions and known issues. Reconcile older feature PRs. | A tester on another Windows machine can launch it, create and share a widget, restore a world, use music and submit a useful problem report. Hold a public rollout if corruption, data loss or material access-control issues remain. | 1–2 days |
| 5. Package and service v1 | Choose one signed installation route. Test WorkerW/desktop attachment early if using MSIX. Exercise install, upgrade from the beta, rollback, uninstall and restoration of user data. Produce versioned release artifacts and update instructions. | Clean VM results, signature verification, upgrade/rollback evidence and a documented recovery procedure. | 6–10 days after a distribution route is chosen |
| 6. Release candidate and public v1 | Benchmark cold/warm startup, idle CPU, working set and refresh latency with 1, 10 and 50 widgets on a named machine. Review logs for sensitive data, finish third-party notices and privacy/help wording. Triage tester feedback, fix blockers and repeat the affected desktop checks on the final artifact. | Identified signed build, green CI, release notes, working distribution path, no unresolved release-blocking defects and explicit known limitations. | 7–12 days plus tester feedback time |

**Schedule.** Steps 1–4 amount to roughly 11–22 developer days. With the soak and security review overlapping where possible, allow **2–4 working weeks for a limited beta**. For a **public v1, budget 6–10 working weeks from this baseline**, including packaging, feedback and retests. At roughly half-time, allow about twice the calendar time. Re-estimate after the first soak and the clean-install packaging trial. A reproducible graphics-driver/SDK fault, delayed signing or a substantial backend remediation could push v1 past this range.

## Platform roadmap beyond v1

These are proposed follow-on milestones. Each can be scheduled independently once the Windows release is stable.

| Milestone | Planned work | Completion test |
| --- | --- | --- |
| Sharing and discovery | Remote gallery/package browsing and remix, richer previews for complex templates, theme remix, file associations, and cleanup of assets still referenced by widgets, scenes or undo history. Keep compatibility with the shipped widget/world formats. Earlier theme/widget extension proposals need a format decision. | Import a remote pack, create an independent copy, move it across machines and remove an unused asset without breaking a saved design or undo. |
| Advanced authoring and runtime | Layer visibility/locking/reparenting, nested groups and bulk selection where supported, keyboard workflows and richer layer/timeline editing. Verify state transitions, formula dependency ordering and cancellation on disable. | Build a clock, launcher, system dashboard and music widget in the editor. Compare editor and host behavior and show actionable errors for invalid expressions. |
| Developer mode | Export tokens to CSS, Tailwind, Style Dictionary and WinUI resources. Add Figma Variables and Windows Terminal output, a generate/apply/export CLI, then consider the optional VS Code preview/autocomplete extension. | Round-trip representative palettes through each advertised format and use the CLI from a clean environment. |
| Extensions and interoperability | Version the plugin API, declare capabilities and trust requirements, document load errors and ship measure/meter/action samples. Scope a Rainmeter import subset and report unsupported directives. Assess isolated hosting separately. | Run the sample in host and editor, diagnose an incompatible extension and produce a compatibility report on a real skin. |
| Broader distribution | Evaluate Store/winget distribution, file associations, a second installer such as WiX, automatic update checks and optional user-initiated crash reports after the first supported release route works. | Verify installation, updates and user-data recovery through each advertised channel. |

**Full platform estimate:** provisionally **another 3–6 months after v1** at the same staffing, for a bounded gallery, developer tools, versioned extension API and a limited importer. Confidence is low until gallery hosting/moderation, plugin trust and import compatibility are scoped. A public marketplace, arbitrary third-party plugin compatibility or an ongoing extension ecosystem has no credible fixed completion date under the current plan.
